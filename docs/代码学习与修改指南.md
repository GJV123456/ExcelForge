# ExcelForge 前后端代码学习与修改指南

本文按当前项目源码整理，说明页面入口、组件、Excel 字段识别、正式规则匹配、样式、接口和数据存储分别在哪里。建议先看“整体请求链路”，再按准备修改的功能看对应章节。

## 1. 先认清目录

当前前端开发目录是 `D:\ExcelForge\frontend`。本地运行前端时在这里执行 `npm.cmd run dev`。

当前联调时使用的完整后端目录是 `D:\ExcelForge\Debug-Table-Auto-backend\backend`。后端通过该目录的 `app.main:app` 启动，正式规则处理代码、目录数据库访问、生成记录和模板写入都在这里。

工作区还存在 `D:\ExcelForge\backend` 和根目录中的其他旧/独立代码目录。修改前应先核对自己启动命令中的 `cd`、`--app-dir` 或当前目录，确保改的是正在运行的那一份。当前用户常用的后端启动目录是上面所说的嵌套 `Debug-Table-Auto-backend\backend`。

## 2. 整体请求链路

```text
浏览器选择 Excel
  → frontend/src/components/UploadExcel.vue
  → frontend/src/utils/excelParser.js 解析表头和行
  → frontend/src/views/Workspace.vue 生成预览数据、提取设备类别/状态
  → frontend/src/api/excel.js 发送 POST /api/v2/excel/process
  → Debug-Table-Auto-backend/backend/app/api/v2/excel.py
  → app/services/formal_processor.py 按目录规则匹配步骤和结果
  → app/db/catalog.py 从 SQLite 查询设备、规则、步骤、结果
  → app/utils/xls_writer.py 按正式模板写入 .xls
  → app/db/generation.py 保存成功记录及文件
```

前端负责读取用户文件、构建请求字段、预览和下载；正式规则命中和 `.xls` 文件写入由后端完成。基础配置页修改的规则写入 SQLite，生成时后端再从同一数据库读取。

正式文件名由 `app/services/formal_processor.py` 生成。前端把上传文件名放在
`sourceFilename` 字段传给后端；后端优先沿用已存在的编号、功能和设备名称，
并把日期更新为生成当天，格式为：

```text
T19-站点-编号-功能-设备具体类型_YYYYMMDD_导入版V1.xls
```

测试地点为“站点”且选择多个站点时，后端会在 `测试地点` 工作表中为每个站点写一行，
而不是只写第一项。`startStation` 仍是首个站点，用于兼容历史接口和历史记录。

## 4. 关键前端数据和处理文件

### Excel 读取与表格类型识别

`frontend/src/utils/excelParser.js`

- `parseExcel(file)`：用 `xlsx` 在浏览器中读取 `.xls/.xlsx`；搜索工作簿各个 sheet 和前 12 行，寻找业务表头。
- `detectExcelType(headers)`：根据必需表头将文件判断为人工处理版 A 或原始设备版 B。
- `buildContent(row, rules)`：将用户在规则生成器配置的字段按顺序拼接成测试内容。
- `extractEquipmentCode(content)`：从测试内容中用正则识别设备编码。
- 文件类型 A 通常直接使用“测试内容”；类型 B 通常需要字段规则拼出测试内容。

如果 Excel 表头识别失败、设备编码提取错、空白尾行被误读，优先从这个文件排查。

### 设备类型、子类型、状态/动作和区间提取

`frontend/src/utils/equipmentSubtype.js`

- 文件中的 `rules` 是前端识别目录：描述某种设备类型/子类型可能对应的关键词和字段。
- `deriveEquipmentClassification(input)` 是主要入口，基于设备类型、设备编码、设备中文、信号描述和测试内容推断分类。
- `deriveEquipmentSubtype(input)`、`deriveEquipmentStatus(input)` 是只取分类中单项信息的辅助函数。
- `extractIntervalName(content)` 从“某某区间上行/下行”文字提取区间名称。
- 工作台把识别出的 `equipmentType`、`equipmentSubtype`、`equipmentStatus`、`intervalName` 等字段放入请求，供后端匹配使用。

想增加设备关键词、补充“故障/火警/预警”等状态识别，先看这个文件中的规则和状态提取实现；同时检查生成请求中相应字段有没有传到后端。

### 工作台的默认值、预览和提交

`frontend/src/views/Workspace.vue`

- `selectedIntegration` 从 Pinia 工作表单 store 读取当前项目；工作台生成请求时将其作为联调项目使用。
- `location` 保存测试地点。当前默认类型为“站点”，默认站点取 `data/stations.js` 的第一项。
- `baseTestContents` 把 Excel 行变成提交/预览对象，并调用 `deriveEquipmentClassification`。
- `parsed()` 接收解析结果、保存行和设置默认拼接规则。
- `submit()` 校验地点与上传数据后调用 `processExcelV2()`，下载后端返回的文件并刷新历史记录。
- 历史记录界面只显示前 5 条，可展开查看接口返回的最近记录。

### 配置页里的规则表单转换和校验

`frontend/src/utils/catalogRule.js`

- 新建规则/步骤/结果的默认表单结构。
- `buildTestContentPayload()` 把页面草稿转换成后端写入格式。
- `validateRuleDraft()` 检查设备类型、测试内容、步骤、结果和责任专业是否完整。
- `getBuiltinStatuses()` 提供部分设备的内置状态名辅助显示。基础配置保存的目录数据仍以数据库内容为准。

配置页的规则列表筛选、步骤旁边“匹配依据”提示、保存/删除操作等页面逻辑在 `frontend/src/views/Config.vue`。API 请求则在下文的 `api/catalog.js`。

### 地点与联调项目默认值

- `frontend/src/data/integrations.js`：联调项目列表、项目代码、名称和对应配置路由。基础配置页读取当前 store 中的项目代码，因此切换项目后规则、站点和责任专业也会跟着切换。
- `frontend/src/store/excel.js`：Pinia 工作台状态；`selectedIntegration` 当前初始化为 `T19`。
- `frontend/src/data/stations.js`：前端地点输入候选站点列表；首项会被工作台作为默认站点。
- `frontend/src/utils/formalLocation.js`：地点类型切换、构建请求中的 `testLocation`、校验站点/区间值。

## 6. 字体和样式放在哪里

### 全局字体、通用控件字号

`frontend/src/styles.css` 是应用全局样式入口，在 `frontend/src/main.js` 中导入。

- `:root` 中的 `font-family` 当前为 `Inter, "Microsoft YaHei", sans-serif`，依次表示优先使用 Inter、Windows 常见的微软雅黑，最后使用系统无衬线字体。
- `font-size` 和 `.el-button`、`.el-input`、`.el-select`、`.el-table`、表单标签等规则控制通用字号。
- 同一文件也包含顶部栏、内容卡片、表单网格、预览、历史记录、地点表单及移动端断点等大部分全局视觉样式。

想统一改整个系统字体，通常改 `styles.css` 的 `:root`；只改登录页或某个组件，可在局部样式中覆盖。字号可能被更具体的 Element Plus 选择器或 scoped 样式覆盖，修改后需检查对应元素的局部规则。

### 各页面样式归属

| 页面/区域 | 样式文件 |
|---|---|
| 顶栏、通用卡片、工作台大部分布局与控件 | `frontend/src/styles.css` |
| 登录页 | `frontend/src/views/Login.vue` 内的两个 `<style>` 块：第一个 scoped，第二个全局覆盖旧样式。 |
| 基础配置页 | `frontend/src/views/Config.vue` 末尾的 `<style scoped>`。 |
| 主框架 Layout | 主要使用 `styles.css` 中 `.app-shell`、`.topbar`、`.main-nav`、`.user-area` 等规则。 |
| LocationForm、UploadExcel 等组件 | 主要使用 `styles.css` 中组件类名规则；查看具体 class 名可在对应 `.vue` 文件中搜索。 |

Vue 文件中的 `<style scoped>` 只作用于当前组件；全局 CSS 没有 scoped 限制。`frontend/src/main.js` 还导入了 Element Plus 自带的 `element-plus/dist/index.css`，全局覆盖规则一般放在自有 `styles.css`。

## 7. 后端：接口入口、规则匹配和正式文件生成

### 后端 API 入口

实际联调目录下：`Debug-Table-Auto-backend/backend/app/main.py`

这里创建 FastAPI 应用并注册认证、目录、历史记录、旧版 Excel 和 v2 Excel 路由。前端正式生成调用的路由文件是：

`Debug-Table-Auto-backend/backend/app/api/v2/excel.py`

其中 `process_excel_v2()` 接收请求，按 formal 模式先调用 `prepare_formal_request()` 补齐目录规则，再生成正式文件，最后将成功记录写入历史数据库并返回文件。

请求字段定义在 `Debug-Table-Auto-backend/backend/app/schemas/excel_v2.py`。例如地点、测试内容、设备类型、设备子类型、状态/动作、区间名、操作步骤和输出结果均在这里定义及校验。

### 后端规则匹配核心

`Debug-Table-Auto-backend/backend/app/services/formal_processor.py`

- `_source_values()`：汇总一行中可供关键词识别的设备中文、生成内容、设备状态、信号描述、区间名称。
- `_interval_context()`：识别“某某区间上行/下行”。
- `_catalog_steps()`：从规则目录候选中确定当前测试内容应该使用的操作步骤与结果。
- `prepare_formal_request()`：对请求中没有显式步骤的数据逐行调用目录匹配，并把匹配出的步骤填回请求。
- `_build_workbook()`：转换为领域对象并做行数、排序等校验。
- `process_formal_request()`：最终调用模板写入器生成正式文件。

当前目录选择逻辑按层级逐步缩小范围：

1. 先按**设备类型**查询候选规则；没有候选时才尝试兼容旧目录中“子类型被保存为设备类型”的情况。
2. 候选中优先匹配**设备子类型**；必要时回退到没有子类型的通用规则；不会随意改用同一大类下另一个不匹配的子类型。
3. 在正确类型/子类型范围中匹配**状态/动作**。请求已带 `equipmentStatus` 时先精确匹配；否则从源文本推断状态/动作，再考虑上/下行方向、规则标题文字等辅助条件。
4. 唯一选中规则后，将步骤和每一步的结果、责任专业带入生成对象。若匹配不到唯一有效规则，会返回目录规则未找到/不完整一类错误，而不是悄悄套用其它状态规则。

因此出现“故障用了预警步骤”时，建议按此顺序检查：前端是否识别出 `equipmentStatus`；请求是否真的包含该字段和正确 `equipmentType/equipmentSubtype`；数据库中的规则是否分别保存了预警、火警、故障状态；再检查 `_catalog_steps()` 的筛选路径。只看页面预览无法证明后端最终命中了哪条目录记录。

### SQLite 目录数据、生成记录和模板

| 文件 | 职责 |
|---|---|
| `Debug-Table-Auto-backend/backend/app/db/catalog.py` | 设备、子类型/状态、规则、步骤/结果、责任专业、站点等目录的读取和写入。规则匹配使用这里的查询接口。 |
| `Debug-Table-Auto-backend/backend/app/db/generation.py` | 保存生成成功的文件、地点、请求摘要和历史记录，提供列表、详情、下载读取。 |
| `Debug-Table-Auto-backend/backend/app/utils/template_provider.py` | 读取并校验正式 Excel 模板。 |
| `Debug-Table-Auto-backend/backend/app/utils/xls_writer.py` | 复制模板样式、写入地点/测试内容/操作步骤/结果，并检查输出结构。 |
| `Debug-Table-Auto-backend/backend/app/domain/workbook.py` | 定义写入器使用的地点、内容、步骤和结果对象。 |
| `Debug-Table-Auto-backend/backend/app/config.py` | formal/mock 模式、数据库和模板路径等后端设置。 |

正式生成时模板本身决定表格版式与样式；`xls_writer.py` 负责保留模板并填入数据。要改输出表格结构/单元格映射优先看 writer 和模板，不要在前端样式文件里找。

## 10. 建议的学习/排查方法

1. 先从页面文件找事件处理函数，例如 Workspace 的 `submit()` 或 Config 的 `saveRule()`。
2. 沿着 API 文件找到请求 URL，再找到对应 FastAPI 路由。
3. 从路由继续跟到 service；service 再调用数据库 repository 或 Excel writer。
4. 判断问题发生在“解析字段”“请求字段”“目录内容”“规则选择”还是“Excel 写入”阶段。每层输入输出不同，先确认字段是否传递正确，能避免改错层。
5. 改规则匹配时运行后端相关测试：`Debug-Table-Auto-backend/backend/tests/test_rule_matching.py` 和 `test_excel_process_v2.py`。改前端解析/分类时运行 `frontend` 目录下 `npm.cmd test`，最后运行 `npm.cmd run build`。

前端测试目录是 `frontend/test/`；后端测试目录是 `Debug-Table-Auto-backend/backend/tests/`。两侧测试覆盖不同职责：前端测试验证解析/分类和表单转换，后端测试验证规则匹配、接口和文件处理。

|---|---|---|
| 前端 | 用户在浏览器里看到、点击、填写的部分 | Vue 页面、按钮、表格、上传控件。源代码在 `frontend/src/`。 |
| 后端 | 浏览器看不到、负责处理请求和业务数据的程序 | Python/FastAPI 服务。实际目录在 `Debug-Table-Auto-backend/backend/`。 |
| 页面 | 一个完整的屏幕区域 | 登录页、数据处理页、基础配置页。通常由 `views/*.vue` 实现。 |
| 组件 | 页面中可重复使用的小块 | Excel 上传框、地点表单、规则编辑器。通常由 `components/*.vue` 实现。 |
| 路由 | 浏览器地址与页面的对应关系 | `/workspace` 显示数据处理页，`/config` 显示基础配置页。 |
| 状态 | 页面运行时暂存的数据 | 当前选中的项目、Excel 行、登录用户。刷新页面后是否保留取决于保存方式。 |
| API/接口 | 前端向后端发请求的地址和格式 | `POST /api/v2/excel/process` 请求后端生成正式表格。 |
| JSON | 前后端交换数据时常用的文本格式 | `{ "equipmentStatus": "故障" }` 是一段 JSON 数据。 |
| 目录/规则库 | 保存设备类型、子类型、测试状态、步骤和结果的数据 | 规则存在 SQLite 数据库中，由基础配置页编辑。 |
| 匹配/命中 | 从多个规则候选中选出适用于当前测试内容的那条 | “吸气式主机 + 故障”应命中故障规则。 |
| 数据库 | 用于长期保存数据的文件或服务 | 当前后端使用 SQLite，具体文件位置由启动时的 `EXCELFORGE_DATABASE_PATH` 决定。 |
| 构建 | 把前端源代码打包成浏览器可以部署运行的文件 | `npm.cmd run build`，输出到 `frontend/dist/`。 |
| 测试 | 自动检查代码是否仍符合预期 | 前端用 Node 测试脚本，后端用 pytest。 |

### 文件名中的缩写

- `.vue`：Vue 页面或组件文件，通常包含逻辑 `<script setup>`、界面 `<template>` 和可选样式 `<style>`。
- `.js`：JavaScript 代码，前端解析、状态、API 调用等逻辑常写在这里。
- `.py`：Python 代码，后端接口、规则匹配、数据库和文件生成逻辑常写在这里。
- `.css`：控制网页外观的样式文件。
- `.json`：结构化数据文本，常用作接口请求示例或测试样例。
- `.xls/.xlsx`：Excel 文件；`.xls` 是较早的 Excel 格式，当前正式模板输出为 `.xls`。

## 12. 新手看代码时的几个基本方法

### 方法一：先找可见文字

如果你在页面看到“测试地点配置”，就在 `frontend/src` 下搜索这段文字。这个文字位于 `views/Workspace.vue` 的模板中。页面文字一般会和附近的 `<el-card>`、`<el-button>` 等标签一起出现。

看到类似下面的代码：

```vue
<el-button @click="submit">生成正式文件</el-button>
```

可以这样读：

- `<el-button>` 是一个按钮。
- `生成正式文件` 是按钮上显示的文字。
- `@click="submit"` 表示点击按钮时调用同一文件脚本里的 `submit` 函数。
- 所以要追踪按钮做了什么，就在当前文件查找 `const submit =` 或 `function submit`。

### 方法二：看组件如何接收和传出数据

```vue
<UploadExcel @parsed="parsed" @clear="clear" />
```

这行把 `UploadExcel.vue` 放进了工作台：

- 子组件在上传并解析成功时发出 `parsed` 事件。
- 工作台监听这个事件，并调用自己的 `parsed()` 函数。
- 这就是“子组件做小任务，再把结果交给父页面”的常见方式。

### 方法三：顺着函数调用往下找

不要只看文件名猜逻辑。比如点生成按钮之后：

1. 在 `Workspace.vue` 找到 `submit()`。
2. 它调用 `processExcelV2()`。
3. 在 `api/excel.js` 找到这个函数，它将请求发到 `/api/v2/excel/process`。
4. 在后端找到 `app/api/v2/excel.py` 中同路径的路由函数。
5. 路由函数调用 `formal_processor.py` 中的生成逻辑。
6. 生成逻辑调用数据库查询和 Excel 模板写入。

这条路线比在所有文件里盲目搜索“故障”更可靠。

### 方法四：先辨别改动属于哪一层

- 如果页面没有显示正确文字或控件：通常是 `.vue` 页面/组件。
- 如果上传后读错列、分类错：通常是 `excelParser.js` 或 `equipmentSubtype.js`。
- 如果预览正确但下载表格内容错：优先检查请求数据、后端规则匹配和模板写入。
- 如果内容正确但颜色、边框、字体错：网页样式看 CSS；Excel 样式看正式模板和 `xls_writer.py`。
- 如果基础配置页保存后刷新又消失：检查前端 API、后端路由和数据库写入。

## 13. 逐页看懂：页面文件中各部分的职责

### 登录页 `views/Login.vue`

这个文件主要做四件事：

1. 保存用户名、密码、登录/注册模式等表单数据。
2. 在点击登录时校验输入。
3. 调用 `api/auth.js` 发送登录或注册请求。
4. 成功后将用户信息放进 `store/user.js`，再跳转到数据处理页面。

页面上“首次使用？创建账号”按钮会切换 `mode` 状态；所以它不一定是另一个单独路由页面，而是同一页面里的另一种显示模式。

### 主框架 `views/Layout.vue`

登录后页面外层的导航栏和用户操作在这里。实际内容区域用 `<router-view>`，也就是由当前 URL 决定加载 Workspace 还是 Config。

如果你要改顶部的“数据处理”“基础配置”、用户名字、退出按钮，先打开此文件；颜色、间距通常再到 `styles.css` 找对应 class。

### 数据处理页 `views/Workspace.vue`

可以把该页面理解成一个流程控制器，它把几个组件按步骤摆放，并在各步骤之间传数据：

1. 从 `store/excel.js` 读取当前联调项目。
2. 显示测试地点组件 `LocationForm.vue`。
3. 显示上传组件 `UploadExcel.vue`。
4. 收到解析行后保存数据，计算预览内容。
5. 点击生成时将地点和每行测试内容发给后端。
6. 下载文件并加载近期生成历史。

页面中的 `computed` 是“根据当前数据自动算出一个值”；例如预览 `preview` 会随着 Excel 行或规则变化而重新计算。`watch` 是“观察某个值，有变化时自动执行一段逻辑”；例如切换项目时刷新历史记录。

### 基础配置页 `views/Config.vue`

这是一个较大的文件，因为规则、设备、责任专业、站点多个配置区域都在同一页。不要被长度吓到，按功能名搜索：

- 找 `activeTab` 和模板中的 `el-tab-pane`：查看各配置标签页。
- 找 `saveRule`：规则保存。
- 找 `loadRules`：加载测试规则。
- 找 `saveEquipment`：保存设备类型/子类型。
- 找 `saveStatuses`：保存子类型的状态/动作。
- 找 `saveDiscipline`：保存责任专业。
- 找 `saveStation`：保存站点。
- 找 `stepMatchBasis`：界面步骤旁的“匹配依据”说明。

该页面负责让人编辑目录数据，不是生成时最终选择规则的唯一位置。最终匹配是在 Python 后端的 `formal_processor.py` 做的。

## 14. 从 Excel 到输出文件：完整实例

假设用户上传一行，内容表示“吸气式主机故障测试”，希望使用数据库中的“吸气式主机/故障”规则。实际处理可以拆为以下阶段。

### 阶段 A：浏览器读取文件

`UploadExcel.vue` 把浏览器选中的文件交给 `parseExcel(file)`。`excelParser.js` 打开工作簿，找到表头和行，然后形成 JavaScript 对象，例如：

```js
{
  sortIndex: 1,
  设备中文: '吸气式主机故障测试',
  设备类型: '监视模块',
  设备编码: ''
}
```

这只是说明数据形状的示例，实际字段以上传表格列名为准。编码为空时仍可能继续生成；编码是否必填由当前业务规则和代码校验决定。

### 阶段 B：工作台整理这一行

`Workspace.vue` 根据输入行生成后端使用的对象。对象中重要字段的含义如下：

| 字段 | 含义 | 常见来源 |
|---|---|---|
| `sortIndex` | 这一条在表中的顺序 | Excel 行顺序。 |
| `generatedContent` | 最终写进正式表格的测试内容文字 | A 版直接取测试内容；B 版由 RuleBuilder 拼接。 |
| `equipmentCode` | 设备编码 | Excel 列或从测试内容中识别。允许空值的文件不要靠编码来判断设备状态。 |
| `equipmentType` | 大类，如监视模块/控制模块 | 原表“设备类型”或分类逻辑。 |
| `equipmentSubtype` | 具体设备，如吸气式主机 | `equipmentSubtype.js` 根据名称、编码、信号等推断。 |
| `equipmentStatus` | 状态或动作，如故障、预警、远程复位 | 从测试内容/信号文字/设备名中推断。 |
| `intervalName` | 区间名称，如“角江路区间”中的区间部分 | 识别“区间上行/下行”内容。 |

前端预览是帮助人检查内容的界面。它不一定会展示所有发给后端的隐含字段，所以需要确认状态是否传对时，查看浏览器开发者工具的 Network（网络）请求，而不是只看预览文本。

### 阶段 C：浏览器发送请求

`processExcelV2()` 使用 JSON 发送数据，响应类型设为 Blob，因为成功响应是 Excel 二进制文件。概念上请求形状类似：

```json
{
  "integrationCode": "T19",
  "testLocation": {
    "type": "站点",
    "direction": "",
    "startStation": "嘉庚体育馆站",
    "endStation": "嘉庚体育馆站"
  },
  "testContents": [
    {
      "sortIndex": 1,
      "generatedContent": "吸气式主机故障测试",
      "equipmentCode": "",
      "equipmentType": "监视模块",
      "equipmentSubtype": "吸气式主机",
      "equipmentStatus": "故障",
      "operationSteps": []
    }
  ]
}
```

说明：这是为了理解字段的简化示例。当前正式规则由后端目录读取时，`operationSteps` 可以留空，后端会尝试自动补齐。若请求已经带了 `operationSteps`，后端会把它视为已提供的规则步骤。

### 阶段 D：后端找规则

后端先看设备类型，再找这个设备类型下面的子类型，然后才在该范围内识别状态/动作。理想候选规则可以理解为：

```text
设备类型 = 监视模块
设备子类型 = 吸气式主机
状态/动作 = 故障
```

“远程复位”属于控制模块的控制动作时，它应该在“控制模块/吸气式主机/远程复位”的规则路径下，而不是与监视模块状态混在一起。设备类型、子类型、状态三者的组合决定规则范围。

### 阶段 E：写 Excel 并保存历史

后端把规则的步骤和结果变为领域数据，然后按正式模板中的列位置和样式写入 `.xls`。成功后将生成记录存入数据库，前端收到二进制文件后触发下载。

如果请求中状态是“故障”，但是输出仍是“预警”步骤，需要逐层对照：

1. `Workspace.vue` 发送的 JSON 里 `equipmentStatus` 实际是什么。
2. `equipmentSubtype.js` 是否从源文字识别出“故障”。
3. 当前 SQLite 数据库是否包含该设备类型/子类型的故障规则。
4. `formal_processor.py` 是否从该候选范围中精确选择故障。
5. `xls_writer.py` 是否把选中的文字正确写入了对应行。

## 15. “关键词识别”和“规则匹配”不是同一件事

这是最容易混淆的地方。可以把流程想成先贴标签，再按标签查规则：

```text
源 Excel 文字
  → 前端识别：设备大类、设备子类型、状态/动作等标签
  → 将标签和原文发送给后端
  → 后端用标签缩小数据库候选规则
  → 后端读取对应操作步骤和输出结果
```

- `equipmentSubtype.js` 做的是前端分类/信息提取，像读文字后给数据贴标签。
- `formal_processor.py` 做的是后端目录规则选择，像拿着标签去数据库查规则。
- `catalog.py` 负责把数据库中的规则记录读出来，不负责浏览器页面上的文字识别。
- `Config.vue` 负责编辑这些规则，但不代替后端最终命中流程。

举例：如果前端没抽取出 `equipmentStatus: "故障"`，后端就只能尝试从其它请求文本中推断；如果数据库里的故障规则把状态写成了别的词，也可能匹配不到。要判断是哪一边的问题，先看请求 JSON，再看数据库目录，最后看服务选择逻辑。

## 16. 用浏览器检查前端到底发了什么

这是排查“前端有没有把关键字发给后端”的实用方法：

1. 在浏览器按 `F12` 打开开发者工具。
2. 选择 **Network/网络** 标签。
3. 清空旧记录（可选），然后在页面重新点“生成正式文件”。
4. 在请求列表中点击 `excel/process`，路径应包含 `/api/v2/excel/process`。
5. 打开 **Payload/Request** 区域，找到 `testContents` 中出问题的那一行。
6. 检查 `equipmentType`、`equipmentSubtype`、`equipmentStatus`、`generatedContent` 是否符合预期。
7. 查看 **Response/响应**：成功时是文件响应；失败时后端通常会返回错误详情。

检查结果的判断：

- 请求中的设备状态已经是“故障”，输出却错误：重点查后端数据库规则和 `_catalog_steps()`。
- 请求中的状态是空或“预警”：重点查 `equipmentSubtype.js` 如何提取状态以及 Workspace 如何组织字段。
- 请求里设备类型/子类型已经错：重点查 Excel 行映射和前端分类规则。
- 后端步骤选择正确，但 Excel 文件单元格显示错：查 `xls_writer.py` 的模板行/列映射。

浏览器 Network 只用于检查这一次实际发出的请求；页面上的预览文字不能代替此检查。

## 17. 如何安全地改代码：以改字体为例

假设你想把全站字体换成微软雅黑优先：

1. 打开 `frontend/src/styles.css`。
2. 找文件开头的 `:root`。
3. 修改 `font-family`，例如 `"Microsoft YaHei", Inter, sans-serif`。
4. 保存后看 `npm.cmd run dev` 的浏览器页面是否热更新。
5. 检查登录页和基础配置页。局部 scoped 样式可能有单独的字号/字体设置，需要按页面实际效果决定是否也修改。
6. 运行 `npm.cmd run build` 确认没有语法错误。

常见 CSS 读法：

```css
.topbar {
  height: 64px;
  background: white;
}
```

- `.topbar` 表示找 HTML 上 `class="topbar"` 的元素。
- `height` 是高度，`background` 是背景。
- 如果样式在 `.vue` 文件的 `<style scoped>` 中，它只影响该组件；如果在 `styles.css` 中，它可能影响所有匹配的元素。
- 修改时优先微调已有规则，避免重复写很多同名选择器造成“改了但看不出效果”。

## 18. 如何安全地改代码：以增加设备关键词为例

假设新增一个设备别名，希望前端把它识别为某子类型：

1. 在 `frontend/src/utils/equipmentSubtype.js` 找到 `rules` 数组中相近设备的规则。
2. 先确认设备所属大类和子类型，不要只添加一个关键词而忘记设备类型。
3. 将新别名放在相应规则 `keywords` 列表中；规则通常需要同时指定匹配后的 `subtype` 和应寻找的状态字段。
4. 检查这些字段是否与基础配置/SQLite 里的设备类型、子类型、状态名称一致。
5. 在 `frontend/test/equipmentSubtype.test.js` 增加输入和期望分类的用例。
6. 运行 `npm.cmd test`；通过后再运行 `npm.cmd run build`。
7. 实际上传一份代表性表格，用 Network 检查请求对象，确认该关键词最终变成了正确字段。

关键词有重叠时要特别小心。例如 `AFC` 同时可能出现在多个字段中。较具体的设备或动作判断要避免被较宽泛的关键词提前吞掉。添加规则后跑测试并检查请求，是防止旧设备分类被新规则影响的关键。

## 19. 如何安全地改代码：以修复状态命中为例

假设“吸气式主机故障”用了预警步骤：

1. 先上传文件并在浏览器 Network 里看请求中的 `equipmentType`、`equipmentSubtype` 和 `equipmentStatus`。
2. 如果状态没传成“故障”，在前端 `equipmentSubtype.js` 查状态提取；用已有的 `equipmentSubtype.test.js` 补一个复现用例。
3. 如果请求三个标签都正确，在正在运行的后端数据库中确认规则的三层目录是否正确：设备类型、子类型、状态/动作。
4. 检查后端目录查询 `app/db/catalog.py` 返回的候选规则，以及 `formal_processor.py` 的选择结果。
5. 在 `Debug-Table-Auto-backend/backend/tests/test_rule_matching.py` 增加“监视模块 + 吸气式主机 + 故障必须选故障步骤”的回归测试。
6. 运行后端 pytest；再重新生成一个文件检查结果。

不要只根据“刚刚改了代码”推断运行中的服务已经使用新代码。若启动命令没有 `--reload`，通常需要先在服务终端按 `Ctrl+C` 停止，再重新启动；若端口仍被占用，要先确认占用 8000 的进程确实是旧服务，避免停错其它程序。是否使用 `--reload` 取决于开发启动方式；它不替代核实启动目录和数据库路径。

## 20. 前后端测试命令和它们检查什么

### 前端

在 PowerShell 中：

```powershell
cd D:\ExcelForge\frontend
npm.cmd test
npm.cmd run build
```

```powershell
cd D:\ExcelForge\Debug-Table-Auto-backend\backend
& .\.venv\Scripts\python.exe -m pytest tests
```

- `pytest tests`：运行后端自动测试。

- `tests/test_generation_history.py`：重点看历史记录。
- `tests/test_template_roundtrip.py`：重点看正式模板读取/输出。

不要把测试目录、虚拟环境、数据库文件当成源码编辑。源码主要在 `app/`；测试用例在 `tests/`；数据库是运行数据；`.venv/` 是 Python 环境。

## 23. 多联调项目隔离设计（T19 与后续项目）

现在系统把“公共流程”和“项目专属资料”分开：

- 公共流程只有一套：上传 Excel、解析表头、构建请求、HTTP 接口、通用规则匹配流程、模板写入、生成历史和页面组件。
- 项目专属资料由联调项目代码区分。当前默认项目代码是 `T19`，页面名称是“ T19联调”。
- 前端项目入口在 `frontend/src/data/integrations.js`；T19 的关键字规则在 `frontend/src/data/integrations/T19/classification.js`。以后新增项目时，新增一个同结构的项目 profile，再在入口文件注册，不复制 `Workspace.vue` 或 `equipmentSubtype.js`。
- `frontend/src/utils/equipmentSubtype.js` 只保留公共分类算法。它根据 `integrationCode` 选择 profile；因此同一套算法可以处理不同项目的关键字。
- 后端目录数据库由 `app/resource_paths.py` 的 `resolve_catalog_database_path()` 选择。T19 继续使用原来的 `excelforge.sqlite3`，保证原数据不丢失；例如项目代码 `T20` 会使用同目录下的 `excelforge.T20.sqlite3`。每个项目的设备类型、子类型、状态/动作、规则、步骤、结果、责任专业和站点都在自己的目录库中。
- 目录表中的 `integration_code` 字段用于明确记录归属；生成历史表中的 `generation_runs.integration_code` 用于筛选历史。前端请求目录和历史时自动附带 `integrationCode`。
- 正式生成时，`formal_processor.py` 按请求中的项目代码打开对应目录库，再按设备类型 → 子类型 → 状态/动作选择规则。项目 A 的规则不会去项目 B 的目录库中查找。

### 新增一个联调项目的步骤

1. 在 `frontend/src/data/integrations/` 新建例如 `T20/classification.js`，导出 `{ rules }`。只放 T20 的设备关键字、子类型和状态/动作别名。
2. 在 `frontend/src/data/integrations/classificationProfiles.js` 注册 `T20` profile。
3. 在 `frontend/src/data/integrations.js` 添加 `{ code: 'T20', name: 'T20联调', ... }`。
4. 为 T20 准备目录数据。可以通过基础配置页面并选择 T20 写入，也可以使用后端导入脚本；首次访问会自动创建 `excelforge.T20.sqlite3`。
5. 用 T20 上传文件生成一次，检查请求中的 `integrationCode`、设备类型、设备子类型和状态/动作，再检查 T20 数据库中的规则。

不要把 T20 的关键词直接追加到公共 `equipmentSubtype.js`，也不要把 T20 规则复制到 T19 数据库。公共算法有改动时才修改公共文件。

### 数据库文件和备份

当前正式启动命令设置的 `EXCELFORGE_DATABASE_PATH` 是 T19 的基础数据库路径。T19 使用该路径；其他项目会在同一目录生成带项目代码后缀的数据库文件。迁移会自动增加项目字段，旧 T19 数据按默认值归入 T19。升级前建议复制整个 `data` 目录备份。

### 旧后端代码能否删除

目前不能直接删除 `D:\ExcelForge\backend`。根目录 `backend/` 仍有旧版兼容接口、依赖和文档引用；另有打包/测试文件可能读取它。你当前启动的正式服务是 `D:\ExcelForge\Debug-Table-Auto-backend\backend`，两者不是同一份代码。

安全处理顺序是：先停止服务并备份，确认没有启动脚本、打包脚本、CI、文档或其他工具引用根目录 `backend/`，再把它移到备份目录观察一轮；确认没有引用后才删除。实际联调后端中的 `app/api/excel.py`、`app/services/excel_processor.py` 和 v1 测试也不能因为“旧”字样直接删除，因为它们仍提供兼容接口。删除前应先删掉调用方和对应测试，跑完整后端测试，再提交版本控制。

## 24. 最后记住这条主线

如果你只记住一条排查路线，可以记住：

```text
看见问题的页面
  → 找页面按钮/输入框的 Vue 文件
  → 找对应的处理函数
  → 找 API 文件和请求字段
  → 在浏览器 Network 验证实际请求
  → 找后端路由和 service
  → 查数据库/模板
  → 补测试，重新生成验证
```

一句话区分各关键层：**前端解析 Excel 并提取标签；后端依据标签从数据库挑选操作规则；写入器把最终数据放进正式 Excel 模板。** 找到问题具体落在哪一段后，再修改对应文件，通常能避免“页面显示没问题，却改错后端”或“后端规则没问题，却改了前端样式”的情况。
